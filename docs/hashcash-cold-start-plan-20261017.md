# 최초 CUDA 준비 개선·난이도 9 비교 계획

기준선은 `63136751f1263c5d4dd80133efe2504bd43ba5ed`이다. 원문과 실행 복사본을 `work/cold-start-20261017`에 보존한다. 이전 난이도 8의 12.29초는 과거 관측이며 이번 난이도 9의 기준선을 새로 측정한다.

목표는 자체 검증·입력 규칙·uint64·기록 저장을 유지하면서 첫 준비 비용을 줄이고, 같은 PC의 실제 웹 난이도 9에서 어떤 모드가 빠른지 판정하는 것이다. GPU 실행은 루트 담당자만 수행한다. 다른 담당자는 읽기 검토와 GPU를 사용하지 않는 구현만 한다. 개인 5187 서버와 SQLite는 측정하지 않고 임시 기록·별도 포트를 사용한다.

## 유한 후보

1. 기준선: 기존 메시지별 digest 8개, 경계 메시지 3개, 탐색 판정 2개, 실제 탐색 특화 20개를 개별 컴파일하는 경로. 실제 첫 준비의 단계·컴파일 횟수·시간을 프로파일링한다.
2. 후보 A: 동일한 33개 CUDA 함수 본문을 이름만 달리하여 단일 RawModule로 묶는다. 자체 검증을 제거하지 않으며 C ABI를 유지한다. NVRTC 호출 감소가 실제 준비 시간 감소로 이어지는지 확인한다.
3. 후보 B: 후보 A가 GPU 단독에도 불필요한 20개 탐색 함수를 한꺼번에 준비하므로, 자체 검증 13개와 필요한 탐색 1·20자리 두 개를 첫 모듈에, C에서만 필요한 나머지 18개를 두 번째 모듈에 묶는다. C ABI·범위 배정은 그대로 두고 GPU의 첫 준비도 줄인다. 처음 검토한 자릿수별 C 범위 분할은 정확성·운영 복잡도가 커 실제 후보에서 제외했다. 이 변경은 B 구현·측정 전에 확정했다.

후보 탐색은 이 둘로 제한한다. 범용 커널 전환이나 검증 삭제·임의 캐시 초기화·전력 설정 변경은 하지 않는다. 선택은 실제 준비 시간과 고정 처리량을 모두 근거로 한다.

## 실험과 판정

- 프로파일은 새 Python 프로세스와 각각 다른 빈 `CUPY_CACHE_DIR`에서 기준선과 후보를 측정한다. CuPy import·장치/할당·self_test·탐색 커널 준비·C 연결을 구분한다. 프로파일러 계측 비용이 있는 진단 결과와 정식 웹 시간을 섞지 않는다.
- 실제 웹 첫 실행은 기본 메시지 `You are the best of best!!!!`, 난이도 **9**, 시작 nonce **0**을 사전 고정한다. 기준선과 선택 후보, GPU 단독/C CPU4+GPU를 각각 새 서버·별도 빈 CuPy 캐시에서 최소 3회 교대 측정한다. 서버별 첫 표본만 최초 실행 집계에 넣는다. OS/드라이버 캐시는 초기화하지 않는다.
- 준비된 재실행은 선택 후보에서 GPU 단독, C CPU4+GPU, Python CPU1+GPU를 **13회씩** 순서 교대한다. 자동 모드는 GPU 우선이라는 구현을 확인한다. 기준선 GPU/C도 같은 입력으로 교대해 비교한다. 모드별 CPU 작업 수는 실제 웹 기본값을 명시한다.
- 고정 계산량은 같은 메시지·난이도9에서 uint64 끝의 **268435456개**를 끝까지 계산한다. 해답이 발생하면 유리한 범위로 바꾸지 않고 실패/운 효과로 보존하고 별도 `search=False` 고정량 검사를 사용한다. GPU/C/Python 동시와 CPU16을 구분한다. CPU 전체 proof 탐색은 사전에 정한 60초 후 실제 웹 중지로 관측을 마치고 미발견을 검열 표본으로 보고한다. 찾은 시간으로 바꾸지 않는다.
- 준비, 준비 제외 첫 해답, 준비 포함 첫 해답, 정리 포함 종료, 화면 표시·저장 완료를 분리한다. 계산 중에는 기존 화면 350ms 상태 요청만 관찰한다. 원시 표본·중앙값·범위·변동·쌍별 승리·완료량·실제 CPU/GPU 겹침·소스 지문을 보관한다.
- 모든 proof는 서버 외에 독립 SHA-256과 브라우저 Web Crypto로 검증하며 정확한 메시지·uint64 문자열·기록 일치를 확인한다. 경계·실패 재시도·취소·재시작·캐시 소유권·실제 스레드 전달 검사, Python·화면·빌드와 독립 검토를 통과한다. 빠른 조건과 느린 조건을 그대로 보고한다.

## 초기 진단 실패와 호스팅 수정

샌드박스 안의 첫 프로파일은 NVRTC 임시 파일 접근 거절로 시작하지 못해 성능 수치에서 제외했다. 승인된 실행에서 별도 캐시로 다시 진행했다. 후보 A의 첫 연결은 CuPy `RawModule.get_function()`이 실제 Function이 아닌 RawKernel을 반환하는 관계를 잘못 처리해 거절됐고, `.kernel`의 Function을 보유하도록 고쳤다. 이 실패도 성공 측정과 구분한다.

첫 임시 웹 호스트는 메인 스레드의 stdin 대기와 보조 스레드 HTTP 루프로 구성했다. POST 뒤 상태 응답과 결과 저장이 나오지 않아 90초에 실패했다. 대기 원인은 로그로 확정할 수 없으며 `baseline-hosting-failed` 자료로 보존한다. 제품과 같이 메인 스레드 `serve_forever()`와 별도 종료 감시를 쓰는 호스트로 바꾼 뒤 전체 기준선을 다시 실행한다. 이 실패를 느린 GPU 성능으로 집계하지 않는다.
