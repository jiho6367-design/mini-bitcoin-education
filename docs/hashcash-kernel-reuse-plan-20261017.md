# CUDA 준비 재사용과 웹 재비교 계획

기준선은 `90ad3365d2575a7109166f4c1dcf9aeeb6f33007`이다. Git archive로 당시 코드를 `work/kernel-reuse-20261017/baseline`에 보존해 같은 PC에서 다시 실행한다. 이전 보고서 수치를 이번 실측으로 사용하지 않는다.

후보는 한 종류로 제한한다. 서버가 정확한 UTF-8 메시지·난이도를 키로 검증된 CUDA 백엔드를 최대 2개 보관한다. 각 백엔드의 C 스케줄러는 CPU 작업 수·배치 설정이 같을 때 재사용하고, 설정이 달라지면 기존 소유자를 종료한 뒤 교체한다. GPU 단독과 C 동시 모드 모두 같은 독점 캐시 정책을 적용한다. 처음 필요한 CUDA 함수를 한 번 컴파일하고 Function·모듈 소유자를 유지한다. nonce·해답·카운터·취소·시간은 작업마다 초기화한다. CUDA/검증 실패 시 대여 종료 후 폐기한다. 사용자 기록은 답으로 재사용하지 않는다.

## 유한 실험

기준선과 후보 각각 실제 Edge 폼으로 아래 네 입력을 측정한다. 각 입력·모드 준비 실행 1회 후 13쌍, 쌍마다 GPU→C / C→GPU 순서를 교대한다. 기준선은 GPU/C 모두 매 작업 새 자원을 만드는 당시 코드 그대로이고, 후보는 GPU/C 모두 캐시를 사용한다. 준비 실행과 원시 값·실패를 모두 보관한다.

| ID | 메시지 | 난이도 | 시작 nonce | 종료 |
| --- | --- | --- | --- | --- |
| easy | `You are the best of best!!!!` | 3 | `0` | 독립 검증 proof |
| ascii | `You are the best of best!!!!` | 8 | `1000000000` | 독립 검증 proof |
| unicode | `한글🙂` | 8 | `1000000000` | 독립 검증 proof |
| fixed | `You are the best of best!!!!` | 64 | `18446744069414584320` | uint64 끝까지 정확히 4294967296개 |

후보 측정 표본은 GPU 자원 재사용, 준비된 native 커널 재사용을 강제 확인하며 C 표본은 C 스케줄러 재사용도 확인한다. 작업 스레드 ID·장치별 완료 수·커널 겹침·실제 nonce·해시·SQLite 저장을 기록한다. 난이도 8과 fixed의 C 표본은 CPU/GPU 모두 실제 계산하고 커널 겹침 하한이 양수여야 한다. 실제 proof 방문 순서는 다를 수 있으므로 동일량 fixed와 별도로 해석한다.

시간은 기존과 같이 준비(`preparationElapsed`), 준비 제외 첫 검증 해답(`proofSearchElapsed`), 준비 포함 첫 해답(`proofElapsed`), 정리 포함 종료(`elapsed`), 화면 표시를 분리한다. 화면의 기존 350ms 응답만 관찰하며 계산 중 추가 상태 HTTP 요청을 만들지 않는다. GPU 센서 조회·독립 후검산·스크린샷은 계산 구간 밖에서 한다.

새 서버·별도 빈 CuPy 디스크 캐시에서 GPU 먼저와 C 먼저의 첫 사용도 각각 1회 확인한다. 재사용은 첫 컴파일 자체를 없애지 않으므로 단발 첫 사용 관측을 준비된 재실행 중앙값과 섞지 않는다. OS/드라이버 캐시를 초기화하거나 사용자 캐시를 삭제하지 않는다.

## 정확성·보존·판정

시작 전에 캐시 LRU·독점 대여·오류 무효화·설정 변경·종료 순서를 CPU 모형으로 검증한다. 실제 GPU에서는 서로 다른 살아 있는 Python 스레드 사이의 동일 자원 전달, NUL·Unicode·uint64 값, C 중지 후 같은 스케줄러로 새 범위 재시작, GPU 단독 전환을 확인한다. 모든 proof는 독립 SHA-256으로 재검증한다.

GPU는 주 담당자만 사용하고 성능 측정과 다른 GPU 검사·CPU 부하 검사를 겹치지 않는다. Windows DWM·브라우저 그래픽 활동과 측정 전후 GPU 상태를 남긴다. 실습용 5187·개인 SQLite는 측정에 사용하지 않으며 별도 포트·임시 기록을 쓴다. 캐시를 제거할 때 C 소유자를 먼저 닫고 CUDA 스트림을 기다린 뒤 버퍼 참조를 해제한다. CuPy의 별도 전역 메모이제이션까지 2개로 제한한다고 주장하지 않는다.

성능 수치와 정확성은 별도 판정한다. 중간값·최솟값·최댓값·변동·쌍별 승리 수·실제 완료량을 보관하고, C가 GPU를 이기지 못하는 조건도 그대로 보고한다. Python·실제 GPU·화면·빌드 검사와 독립 코드/자료 검토를 통과한다.

## 기준선 복사본 준비 오류와 복구

Windows에서 만든 Git archive의 C/H 파일은 CRLF였고 기존 빌드 메타데이터는 원본 커밋과 작업 폴더의 LF 바이트 해시를 보관했다. 첫 기준선 실행은 이 차이로 DLL 검증에서 거절되어 CPU로 전환했다. 이 실행은 `baseline-setup-rejected.json`에 실패 자료로 보존하며 성능 집계에 포함하지 않는다. 네 C/H 파일의 줄바꿈을 정규화한 내용이 기준선 커밋·현재 소스·복사본 모두 같음을 확인하고, 원래 빌드와 일치하는 LF 바이트를 복사본에 복원했다. 메타데이터 검사를 우회하거나 C 연산 코드를 수정하지 않고 동일한 유한 비교를 처음부터 다시 실행했다. 패키징 때 Git 원문·zip 원문·실행 시 지문·빌드 메타데이터를 재대조해 LF/CRLF 방향 설명도 바로잡았다.

## 오류 경로 검토 후 최종 후보 재측정

후보의 첫 112개 실행은 정상 완료했지만, 별도 코드 검토에서 C가 유효한 proof와 `cleanup_warning`을 함께 반환하는 경우 캐시 소유자를 폐기해야 한다는 점을 확인했다. proof·기록은 보존하면서 해당 C/CUDA 자원은 대여 종료 후 폐기하도록 오류 경로를 보강한다. 이 회귀 검사를 통과한 최종 코드로 같은 4개 입력·준비 실행·13쌍을 다시 측정한다. 이전 112개와 당시 소스는 `candidate-pre-hardening` 자료로 남기며 유리한 반복 결과를 골라 쓰지 않는다.
