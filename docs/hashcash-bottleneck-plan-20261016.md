# 추가 병목 조사와 유한 후보

기준선은 `8cd2e73f1f18323a6257e0d329c42218bca6a1d5`이다. 원본 gpu/hybrid/cpu/server를
`work/bottleneck-baseline/`에 Git에서 그대로 보존한다. 참가자 DB는 사용하지 않는다.

1. 같은 1,073,741,824개 nonce, 28바이트 ASCII, 10자리 시작값, 난이도 5에서 GPU 단독과
   기존 hybrid 1/4/15 CPU, 대기 루프 수정 hybrid 1/4/15 CPU를 7회 교대 비교한다.
   CPU 제출/시작/완료/결과 전달/수신과 GPU host/kernel 시간, 마지막 GPU 이후 반환을 나눈다.
2. 대기 수정 후 CPU batch 50,000 / 250,000 (CPU 1/4개), GPU batch
   16,777,216 / 67,108,864를 비교한다. 고정 계산량을 끝까지 처리하며 tail을 포함한다.
3. GPU 커널 후보는 명시 funnelshift/lop3, packed ASCII 증가 두 개로 제한한다.
   기존 커널과 동일한 nonce를 전부 처리하고 자체 검증/독립 SHA-256을 통과해야 한다.
4. 네이티브 CPU 후보는 기존 GCC/OpenSSL의 C 범위 루프 하나로 제한한다.
   ctypes 호출로 Python per-nonce 비용을 없애고 CPU 1/4/8개 구성을 비교한다.
   미리 생성된 동일 Pool, DLL, CUDA를 사용하고 준비 시간은 별도 기록한다.
   1차 native process 비교 후, IPC 영향을 분리하려고 같은 1/4/8개 thread 구성을
   사전 후보로 추가한다(측정 전 추가). ctypes의 실제 C 호출만 GIL을 해제한다.
5. 탐색에서 유망한 후보만 별도 13회 재확인한다. 한국어, 20자리 nonce와 난이도 3/7도
   확인한다. 처리량 증가와 proof 발견/중단 지연을 구분한다. 동시 모드가 GPU 단독을
   이기지 못하면 그대로 기록하고 자동 선택 기준을 바꾸지 않는다.

추가 검증 전에 난이도 8의 동일 28바이트/10자리 입력 한 개를 고정 후보에 추가한다.
난이도 7은 16M, 8 이상은 64M을 채택할 경우 실제 적용할 8자리 target 조건도
별도 13회 확인하기 위함이다. 후보를 무제한 탐색하는 대신 이 여섯 profile에서 마친다.

native 50k가 GPU 배치보다 먼저 끝나는 할당 공백도 확인되어 마지막 후보 하나를 추가한다
(추가 측정 전 고정). CPU 250k / GPU 64M으로 연산 시간을 맞추고 마지막 GPU 두 배치에는
CPU 신규 할당을 억제하는 실험 allocator에서 process/thread 1/4/8을 13회 비교한다.
이 후보 뒤에는 추가 탐색을 끝낸다. 최종 승자가 없으면 native 경로는 실험에만 남긴다.

GPU 측정은 루트 담당자만 실행한다. 다른 의도적 GPU/CPU 부하와 겹치지 않게 한다.
전력/온도 끝점만으로 전력 제한을 원인으로 단정하지 않는다. 성공 조건은 정확한 범위,
실제 동시 실행, 독립 해시 검증, 반복 실측, 관련 회귀 검사와 독립 검토이다.
