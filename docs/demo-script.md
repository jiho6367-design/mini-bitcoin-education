# 5~7분 시연 대본과 예상 질문

## 사전 준비

1. 시연 전에 `frontend` 폴더에서 `npm.cmd run build`로 화면을 빌드해 둔다. 시연할 때는 `backend` 폴더에서 `uv run mini-bitcoin-backend` 하나만 실행하고, 터미널에 **화면과 API를 함께 제공합니다**가 표시되는지 확인한 뒤 Chrome/Edge로 `http://127.0.0.1:8000`을 연다. 시연 중에는 이 터미널을 닫지 않는다. 백엔드를 다시 시작하면 진행 중인 실습이 사라지므로 시작 화면에서 새로 시작한다.
2. 브라우저 확대 비율을 발표 화면에 맞게 조절한다. 난이도 1에서 저속 학습과 수동 전달로 관찰하고, 오래 걸리면 빠른 실행으로 마무리한다. 높은 난이도의 저속 실행은 시연 시간에 적합하지 않을 수 있다. 채굴 중에는 채굴 화면의 탭을 앞에 둔다. 탭이 뒤에 있으면 계산 요청이 늦어진다.
3. 네트워크 전달과 변조까지 직접 진행한다. 성공 시간을 미리 보장하지 않는다.
4. 화면 캡처는 `docs/screenshots/`에 보관한다. 최종 영상 녹화 파일은 이번 산출물에 포함하지 않는다.

첫 실제 해시가 성공하면 그대로 설명한다. 실패 장면을 연출하려고 정답을 무시하지 않는다. 오래 걸리면 중지 후 빠른 연속 실행을 사용하거나 난이도 1의 새 실습을 시작한다. 다음 거래의 금액을 바꿨을 때 이전 Blockchain 완료 표시가 초기화되는 것도 확인한다. 정상 흐름 영상과 난이도 비교 영상은 분리 촬영해도 된다.

## 예상 질문

**Q. 왜 화면과 백엔드를 나누었나요?**  
A. 규칙을 한 곳에만 두고 화면과 분리해 설명하기 위해서입니다. 서명·검증·채굴·노드 상태는 모두 Python 백엔드가 처리하고, 화면은 그 결과를 보여 주며 조작을 요청으로 보냅니다. 브라우저에는 서명이나 해시 코드가 없습니다. 1.1.0까지는 같은 규칙이 브라우저 안의 TypeScript로 있었고, 옮긴 Python 구현이 같은 서명·해시·검증 결과를 내는지 기준값으로 검사했습니다.

**Q. 실행할 때 서버가 몇 개 필요한가요?**  
A. Python 백엔드 하나입니다. 화면을 한 번 빌드해 두면 백엔드가 그 파일과 API를 같은 주소에서 함께 제공합니다. Node.js는 화면을 빌드하거나 수정할 때만 필요하고, 수정 중에는 화면 개발 서버를 따로 실행해 바로 확인합니다.

**Q. 왜 DB가 없나요?**  
A. 목표가 한 PC에서 처리 원리를 관찰하는 것이기 때문입니다. 실습 상태는 백엔드의 메모리에만 두며, 새로고침하거나 백엔드를 다시 시작하면 초기화합니다. 브라우저에는 화면 테마 선택값만 저장합니다.

**Q. 백엔드가 있으니 이제 분산 시스템인가요?**  
A. 아닙니다. 나눈 것은 화면과 규칙이지 노드가 아닙니다. 세 노드는 백엔드 프로세스 하나 안에서 각자의 상태로 독립 검증을 수행하고, 전송은 메모리 메시지 대기열입니다. 네트워크 장애와 합의의 모든 특성을 재현했다고 주장하지 않습니다.

**Q. 개인키를 서버가 가지고 있어도 되나요?**  
A. 실제 지갑이라면 안 됩니다. 실제 지갑은 사용자의 기기에서 서명하고 개인키를 내보내지 않습니다. 이 작품은 규칙을 한 곳에 두려고 백엔드가 교육용 키를 보관하고 서명하며, 이 PC 안에서만 동작합니다. 개인키는 실습 상태·메시지·이벤트에 넣지 않고, 펼쳐 보기를 열 때만 화면으로 보냅니다. 이 차이를 화면과 문서에 명시했습니다.

**Q. 백엔드는 혼자서 계속 채굴하나요?**  
A. 아닙니다. 화면이 계산을 요청할 때마다 백엔드가 다음 Nonce들을 실제로 계산해 돌려줍니다. 서버에 스레드나 타이머를 두지 않아 구조가 단순하고, 탭을 닫으면 계산도 멈춥니다. 대신 화면 없이 채굴이 진행되지는 않습니다.

**Q. 잔액 숫자만 빼면 더 쉽지 않나요?**  
A. Bitcoin의 UTXO와 이중 지출 개념을 유지하려고 입력 소비와 새 출력 생성으로 구현했습니다. 화면은 잔액을 쉽게 보여주고 상세 보기에 UTXO를 드러냅니다.

**Q. 왜 30을 보내는데 100이 잠기나요?**  
A. 입력으로 선택한 100짜리 출력 전체를 소비하기 때문입니다. 새 30 출력과 70 거스름돈 출력은 블록에 들어간 뒤 사용할 수 있습니다. 이번 모델은 미확정 출력의 재사용을 제외했습니다.

**Q. 서명은 무엇을 보장하나요?**  
A. 해당 개인키의 소유자가 특정 거래 원문에 서명했음을 검증합니다. 금액 부족·이중 지출은 서명만으로 판단할 수 없으므로 노드 상태 검증도 필요합니다.

**Q. 난이도가 높으면 매번 더 오래 걸리나요?**  
A. 평균적으로 더 많은 시도가 필요합니다. 하지만 개별 결과는 확률적이므로 한 번의 실행으로 비교하면 안 됩니다.

**Q. 채굴 보상이 없는데 왜 채굴하나요?**  
A. 이 작품은 보상 경제보다 작업증명과 기록 과정을 가르칩니다. 보상을 제외한 점을 명시했고, 초기 학습용 코인은 Genesis에서 배정합니다.

**Q. 과거 기록은 절대로 바꿀 수 없나요?**  
A. 데이터를 수정할 수는 있지만 검증에 실패합니다. 실제 Bitcoin에서 유효하게 바꾸려면 서명 규칙을 만족하는 거래와 후속 작업증명·체인 선택 조건을 만족해야 합니다. 이 실습은 그중 검증·해시 연결을 보여줍니다.

**Q. 어떻게 테스트했나요?**  
A. 백엔드는 pytest로 핵심 함수의 정상·부정 입력, 원자적 블록 반영·노드 독립성, 채굴 작업의 단계·일시정지·시간 집계, HTTP API를 검사했고, 1.1.0 TypeScript 구현의 기준값을 Python 구현이 재현하는지도 확인했습니다. 화면은 단위 테스트와, 설치된 Chrome/Edge에서 실제 백엔드를 함께 실행한 브라우저 테스트로 검증했습니다. 정확한 결과는 테스트 기록에 기재했습니다.
