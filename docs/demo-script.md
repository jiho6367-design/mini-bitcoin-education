# 5~7분 시연 대본과 예상 질문

## 사전 준비

1. `npm.cmd run build`와 `npm.cmd run preview`를 실행하고 Chrome/Edge를 연다.
2. 브라우저 확대 비율을 발표 화면에 맞게 조절한다. 난이도 1에서 저속 학습과 수동 전달로 관찰하고, 오래 걸리면 빠른 실행으로 마무리한다. 높은 난이도의 저속 실행은 시연 시간에 적합하지 않을 수 있다.
3. 네트워크 전달과 변조까지 직접 진행한다. 성공 시간을 미리 보장하지 않는다.
4. 화면 캡처는 `docs/screenshots/`에 보관한다. 최종 영상 녹화 파일은 이번 산출물에 포함하지 않는다.

첫 실제 해시가 성공하면 그대로 설명한다. 실패 장면을 연출하려고 정답을 무시하지 않는다. 오래 걸리면 중지 후 빠른 연속 실행을 사용하거나 난이도 1의 새 실습을 시작한다. 다음 거래의 금액을 바꿨을 때 이전 Blockchain 완료 표시가 초기화되는 것도 확인한다. 정상 흐름 영상과 난이도 비교 영상은 분리 촬영해도 된다.

## 예상 질문

**Q. 왜 백엔드나 DB가 없나요?**  
A. 목표가 한 PC에서 처리 원리를 관찰하는 것이기 때문입니다. 핵심 로직을 화면에서 독립된 모듈로 만들고, 상태를 가진 모의 노드 세 개를 사용했습니다. 지갑·거래·블록체인 등 실습 상태는 새로고침 시 초기화하며 화면 테마 선택값만 저장합니다.

**Q. 세 노드가 동일 브라우저 안에 있는데 분산 시스템인가요?**  
A. 실제 분산 환경은 아닙니다. 세 노드는 상태 사본과 독립 검증을 수행하지만 전송은 메모리 메시지 대기열입니다. 네트워크 장애와 합의의 모든 특성을 재현했다고 주장하지 않습니다.

**Q. 잔액 숫자만 빼면 더 쉽지 않나요?**  
A. Bitcoin의 UTXO와 이중 지출 개념을 유지하려고 입력 소비와 새 출력 생성으로 구현했습니다. 화면은 잔액을 쉽게 보여주고 상세 보기에 UTXO를 드러냅니다.

**Q. 왜 30을 보내는데 100이 잠기나요?**  
A. 입력으로 선택한 100짜리 출력 전체를 소비하기 때문입니다. 새 30 출력과 70 거스름돈 출력은 블록에 들어간 뒤 사용할 수 있습니다. 이번 모델은 미확정 출력의 재사용을 제외했습니다.

**Q. 서명은 무엇을 보장하나요?**  
A. 해당 개인키의 소유자가 특정 거래 원문에 서명했음을 검증합니다. 금액 부족·이중 지출은 서명만으로 판단할 수 없으므로 노드 상태 검증도 필요합니다.

**Q. 난이도가 높으면 매번 더 오래 걸리나요?**  
A. 평균적으로 더 많은 시도가 필요합니다. 하지만 개별 결과는 확률적이므로 한 번의 실행으로 비교하면 안 됩니다.

**Q. 채굴 보상이 없는데 왜 채굴하나요?**  
A. 이 작품은 보상 경제보다 작업증명과 기록 과정을 가르칩니다. 보상을 제외한 점을 명시했고, 초기 학습용 코인은 Genesis에서 배정합니다.

**Q. 과거 기록은 절대로 바꿀 수 없나요?**  
A. 데이터를 수정할 수는 있지만 검증에 실패합니다. 실제 Bitcoin에서 유효하게 바꾸려면 서명 규칙을 만족하는 거래와 후속 작업증명·체인 선택 조건을 만족해야 합니다. 이 실습은 그중 검증·해시 연결을 보여줍니다.

**Q. 어떻게 테스트했나요?**  
A. 핵심 함수의 정상·부정 입력 단위 테스트, 원자적 블록 반영·노드 독립성 통합 테스트, 설치된 Chrome/Edge의 실제 Worker를 포함한 브라우저 테스트로 검증했습니다. 정확한 결과는 테스트 기록에 기재했습니다.
