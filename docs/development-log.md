# 블록체인 실습실 개발 기록

기준일 **2026-11-17** · 팀 브랜치 `blockchain-practice` · 앱 `3.0.0` · 교육 엔진 `3.2.0`

## 현재 구성과 결정

팀 앱의 화면과 API는 `experiments/blockchain-practice/` 안의 Flask 서버 하나가 제공합니다 기초 실습은 계정 잔액 모델, 공동 실습은 UTXO 모델이며 규칙과 장부를 구분합니다 개인 본체에서 가져온 엔진·화면은 독립 사본으로 관리하고 출처 해시는 [PROVENANCE](../experiments/blockchain-practice/education_engine/PROVENANCE.json)에 보존합니다

사용자가 처음 볼 화면은 기초 실습입니다 공개 메뉴는 **기초 실습 → 공동 실습 → 넌스 찾기**로 정리했습니다 이전 통합 화면은 `/advanced`에 보존하며 공개 메뉴에 별도의 중복 탭을 두지 않습니다 기초·공동·넌스는 공통 색상과 테마 설정을 사용합니다

운영 기록은 Neon PostgreSQL에 저장합니다 Render 앱을 다시 시작하거나 교체해도 같은 DB·접속 정보·방 링크를 사용합니다 로컬에서는 분리된 SQLite 파일을 사용합니다 저장소 키·쿠키·DB 접두어와 이전 주소의 접속 이전 설정은 제품 이름 변경과 구분해 보존했습니다

## 2026-11-17 · 문서와 기록을 현재 팀 앱 기준으로 정리

루트 문서에는 초기 개인 React 앱의 백엔드·DB·저장·공동 실습 부재와 구 화면 캡처가 남아 있었습니다 정리 전 문서와 과거 테스트 결과는 [개인 React 보관 자료](archive/personal-react/README.md)로 옮기고, 현재 사용 안내·설계·요구사항·보고서·시연 대본을 실제 팀 앱 코드에 맞췄습니다

이번 정리는 기능을 추가하거나 패키지를 갱신하는 작업이 아닙니다 앱 버전과 운영 코드는 유지하며 [배포 상태](release-status.json)에 마지막 확인한 운영 커밋 `9fca791`을 명시합니다 과거 테스트 숫자·화면·검증 한계는 당시 자료로 보관하고 새 결과를 만들어 채우지 않습니다

## 2026-11-16 · 입장·학습 순서와 채굴

- 기초 실습을 메인으로 정하고 기존 통합 실습의 세 노드 채굴 비교를 기초 장부에 연결
- 공동 실습은 기존 링크 입장과 새 실습 만들기로 구분하고 별명·현재 참가자·역할을 보이도록 개선
- 혼자라면 팀 A 하나로 쉬운 실습을 진행하도록 다음 동작을 안내하고, 대기 거래가 있으면 새 송금을 강요하지 않고 채굴을 이어감
- 공통 가이드의 완료 상태를 실제 거래·역할·전파·유효 체인 일치에 따라 계산
- 새 방의 팀별 초기 금액을 선택하되 기존 기본 방·저장 장부는 유지
- 한 노드 채굴과 세 후보 경쟁을 구분하고 공통 실행 제어를 교사 접속과 분리

## 2026-11-16 · 저장·무료 배포·자동 재연결

- 개인 본체의 UTXO·서명·수수료·보상 성숙·경쟁·보관함·공동 실습 코드를 팀 앱 안에 독립 사본으로 통합
- 로컬 SQLite 저장과 운영 Neon PostgreSQL 저장을 구분하고 소유자·권한·저장 실패 원복·단일 쓰기 프로세스 경계를 검증
- Render Free와 Neon Free를 사용하며 유료 영속 디스크 없이 앱 교체 뒤 복원 확인
- 교사 없이 같은 방 링크로 참여하고, 연결을 잃어도 입력을 유지하며 서버가 준비되면 읽기를 자동 재연결
- 처리 여부가 불확실한 거래·채굴·저장 명령은 자동으로 반복하지 않도록 유지

## 2026-11-15 · 자료 확보와 초기 검증

원본 추가 파일과 전체 프로젝트를 확보해 별도 브랜치에서 실행했습니다 누락·만료 자료 확인, 원본 실행, 초기 영상과 테스트 정리는 [상세 검증 이력](../experiments/blockchain-practice/VERIFICATION.md)에 당시 상태로 보존합니다

## 버전과 검증 기록 규칙

1. 현재 팀 앱 버전의 기준은 팀 `frontend/package.json`이며 `app.py`의 `APP_VERSION`과 잠금 파일의 프로젝트 버전을 맞춥니다 루트 개인 모델 버전은 따로 관리합니다
2. 기능·호환성 변경을 실제로 출시할 때 버전을 정하고 변경 내역을 남깁니다 문서 정리나 브랜치 이름 변경을 이유로 존재하지 않았던 버전을 소급하지 않습니다
3. 테스트 기록에는 날짜·커밋·명령·통과·건너뜀·실패와 실제 확인 범위를 함께 기록합니다 목록 수집과 테스트 실행, 과거 전체 실행과 부분 재실행을 구분합니다
4. 운영 코드를 바꾸면 컨테이너·저장 복원 검증을 확인하고 같은 DB·보안 키·방 링크를 보존합니다 이번 문서 정리의 링크 검사로 앱 전체 검증을 새로 수행했다고 주장하지 않습니다
5. 비공개 상태 파일·키·실제 접속 쿠키·DB 연결값을 공개 문서에 넣지 않습니다
