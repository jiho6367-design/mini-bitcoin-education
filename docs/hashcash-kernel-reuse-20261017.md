같은 입력을 다시 실행할 때 C 모드의 준비 중앙값을 **11.650 → 0.404ms, 96.53%** 줄였다. GPU 단독에도 같은 재사용 정책을 적용해 비교했으며, 기본 메시지 난이도 8의 **준비 포함 첫 해답 수신은 GPU 488.076ms → C CPU4+GPU 460.817ms, 5.59% 단축**이었다. 교대 실행한 13쌍 모두 C가 빨랐다. 최초 컴파일 비용은 남아 있으며, 빈 임시 CuPy 캐시에서 C 첫 준비는 **12.289초**였다.

## 구현과 유지 조건

- 서버가 정확한 `(UTF8(message), difficulty)`를 키로 CUDA 백엔드를 최대 2개 보관한다. 공백·줄바꿈·NUL·Unicode를 정규화하지 않는다. 고정된 장치·커널 설정의 캐시이며 LRU로 오래된 소유자를 정리한다.
- C가 쓰는 1~20자리 CUDA Function과 모듈 소유자를 한 번 준비해 유지한다. C 스케줄러도 CPU 수·CPU/GPU 배치·trace 설정이 같으면 재사용한다. 설정이 달라지면 기존 C 소유자를 닫고 새로 연결한다. C 코드와 DLL은 변경하지 않았다.
- GPU 단독·자동·Python 동시·C 동시 경로가 같은 독점 대여를 사용한다. CUDA 컨텍스트를 보존해 순차적인 다른 Python 작업 스레드에서도 같은 자원을 사용한다. C 호출과 감시 스레드가 끝난 뒤 대여를 반환한다.
- 매 작업의 범위·해답·카운터·취소·시간은 초기화한다. 발견 기록을 답으로 재사용하지 않는다. 기존 `SHA256(UTF8(message) || ASCII(decimal_nonce))`, 선행 16진수 0 난이도와 문자열 uint64 규칙을 유지한다.
- GPU 실패·잘못된 proof·C 연결 실패·C의 해답 보존 후 정리 오류에는 캐시를 무효화한다. 유효한 해답과 기록은 보존하고 자원만 폐기한다. C 소유자를 먼저 닫고 CUDA 스트림을 기다린 뒤 참조를 해제한다. 종료 중에는 새 작업을 받지 않는다.

재사용은 같은 서버 프로세스 안에서 유효하다. 다른 메시지·난이도, 캐시 축출, 오류 후 폐기, 서버 재시작은 준비가 다시 필요할 수 있다. CuPy 자체의 전역 모듈 캐시는 별개이므로, 이 제한이 전체 GPU 모듈·VRAM을 두 개로 제한한다는 뜻은 아니다. 진단용 `HASHCASH_GPU_REUSE=0`으로 재사용을 끌 수 있다.

## 실패·검증·재현

Windows Git archive의 네 C/H 파일이 CRLF로 나가 기존 LF 빌드 지문과 달랐던 첫 기준선은 CPU로 전환되어 비교 도구가 거절했다. 원본 커밋·현재 소스·복사본의 줄바꿈 정규화 후 내용 일치를 확인하고 원래 LF 바이트를 복원했다. 정식 기준선은 DLL 메타데이터와 원본 커밋의 해시가 모두 일치하며 검사를 우회하지 않았다. 실패 2표본도 보관했다.

첫 후보 112회가 정상 완료한 뒤 독립 코드 검토에서 해답과 `cleanup_warning`을 함께 반환하는 오류 경로의 캐시 폐기가 빠졌음을 발견했다. proof 보존·자원 폐기 회귀 검사를 추가해 고친 뒤 같은 네 입력·13쌍을 모두 다시 실행했다. 수정 전 112회와 소스도 보관했다. 수정 전 한글의 준비 포함 C 해답은 GPU보다 1.58% 늦었고 6/13쌍만 이겼다. 최종 결과만 유리하게 골라 재시도한 것은 아니다.

- 실제 GPU/CUDA를 포함한 Python **158개 통과**, 건너뜀 없음. 다른 살아 있는 작업 스레드로 자원 전달, NUL·Unicode·uint64 독립 검산, C 취소 후 같은 소유자로 정확히 100003개 재시작, 오류 무효화·LRU·종료 검사를 포함한다.
- TypeScript·ESLint·Vitest **41개**·배포 빌드 통과. 실제 CUDA/C를 포함한 Edge 화면 검사 **8개 통과**. 같은 입력 재사용·공백 변경·LRU 내 복귀·브라우저 검증·각 새 기록을 확인했고 화면 이미지도 점검했다.
