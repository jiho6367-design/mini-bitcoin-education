검증일: **2026-10-16 한국 시간**. 기준 코드는 이 저장소의 `0daf95a59172ac92219d51f3033d6c667c5c4f68`입니다. 10월 3일의 교사 원본 비교와 별도로, **이미 개선한 현재 코드를 더 개선할 수 있는지** 확인했습니다.

- **CPU + GPU 동시 모드**를 구현했고 양쪽의 실제 계산 중첩을 확인했습니다. 이번 Python CPU·CUDA 구현의 실측에서는 GPU 단독이 더 빨랐습니다.

## 장비와 비교 조건

Intel Core Ultra 7 356H, 논리 프로세서 16개, NVIDIA GeForce RTX 5070 Laptop GPU, Windows 11, Python 3.13.15, CuPy 14.2.0, CUDA 12.9 환경입니다. 드라이버는 591.74입니다. 하드웨어·드라이버·전력 설정을 변경하지 않았습니다.

모든 계산은 `SHA256(UTF8(message) || ASCII(decimal_nonce))`입니다. 난이도는 선행 16진수 0 개수입니다. 고정 계산량 비교는 해답을 발견해도 같은 집합을 끝까지 계산하며, proof와 마지막 해시는 독립 `hashlib`으로 확인했습니다. 초기화·컴파일·프로세스 생성이 제외된 계산 처리량과 실제 탐색의 경과 시간은 구분합니다. 아래 서로 다른 실험 표의 절대 GH/s를 서로 나누어 추가 개선율을 만들면 안 됩니다.

## GPU 단독 추가 최적화

기존 코드는 배치마다 CUDA 이벤트를 만들고, 결과 flag·nonce·digest를 각각 읽으며 동기화를 반복했습니다. 새 코드는 정렬된 **48바이트 장치 결과 버퍼 하나**, **재사용하는 pinned 호스트 버퍼 하나**, **재사용하는 이벤트 두 개**를 사용합니다. 같은 스트림의 blocking readback이 커널 완료를 보장하므로 그 앞의 중복 동기화를 제거했습니다.

CUDA 해시 커널은 바꾸지 않았습니다. 5개 프로필의 search·dump 생성 소스가 기준선과 바이트 단위로 같은 것을 확인했습니다. 기존 자체 검증과 발견 proof 검증을 유지했습니다.

동일 배치·268,435,456회/표본·**13회 교차 순서의 별도 재확인** 결과입니다.

| 입력 조건 | 기준 GH/s | 개선 GH/s | 중앙값 비율 | 개선이 빨랐던 반복 |
|---|---:|---:|---:|---:|
| ASCII 28바이트, nonce 10자리, 난이도 5 | 2.829 | 3.117 | 1.102배 | 12/13 |
| 한국어, nonce 10자리, 난이도 5 | 2.802 | 3.093 | 1.104배 | 12/13 |
| ASCII 28바이트, nonce 20자리, 난이도 5 | 2.624 | 2.791 | 1.064배 | 12/13 |
| ASCII 28바이트, nonce 10자리, 난이도 7 | 3.319 | 3.520 | 1.061배 | 10/13 |
| ASCII 28바이트, nonce 10자리, 난이도 3 | 0.625 | 0.808 | 1.293배 | 13/13 |

난이도 5는 기존 4,194,304회 배치, 7은 8,388,608회, 3은 262,144회 배치를 그대로 사용했습니다. 단순히 배치를 키워 과잉 계산을 늘린 결과가 아닙니다. 각 표본은 50ms 이상입니다. Windows·GPU 클럭 변동이 있으며 CV와 짝별 비율도 기록했습니다. 특히 난이도 3은 변동이 상대적으로 큽니다. 초기 준비와 확률적인 실제 발견 시간이 위 비율만큼 줄어든다고 주장하지 않습니다.

15개 launch geometry 후보도 시험했습니다. 일부 입력에만 유리했던 128 threads × 16 trials는 낮은 난이도에서 느려 기존 **256 × 16**을 유지했습니다. 단일 pageable 버퍼 후보와 pinned 후보의 탐색·확인·별도 재확인을 모두 [GPU 원시 보고서](hashcash-optimization-gpu.json)에 남겼습니다.

## CPU + GPU 동시 모드

중앙 할당자가 서로 다른 연속 nonce 구간을 CPU 프로세스와 GPU에 줍니다. GPU는 자리수와 uint64 경계를 먼저 잘라 예약합니다. 실패한 GPU 구간만 CPU 재시도 큐에 넣고, 이미 완료한 구간은 다시 세지 않습니다. 자동 모드는 기존처럼 CUDA를 우선 사용하며 동시 모드는 직접 선택합니다. 화면에서 동시 모드를 고르면 CPU 작업 1개로 시작하고 사용자가 늘릴 수 있습니다.

실제 서버의 난이도 5 배치 정책, ASCII 28바이트 기본 메시지, 시작 nonce 1,000,000,000, **동일한 1,073,741,824개 nonce**, GPU 배치 4,194,304·CPU 배치 10,000, warmed 프로세스 풀, **13회 교차 순서**의 결과입니다.

| 구성 | 중앙값 GH/s | GPU 단독 대비 | GPU 단독보다 빨랐던 반복 |
|---|---:|---:|---:|
| 개선 GPU 단독 | **3.446** | 기준 | — |
| GPU + CPU 작업 1개 | 3.119 | 0.905배 | 0/13 |
| GPU + CPU 작업 2개 | 3.015 | 0.875배 | 0/13 |
| GPU + CPU 작업 4개 | 2.738 | 0.795배 | 0/13 |
| GPU + CPU 작업 8개 | 2.547 | 0.739배 | 0/13 |
| GPU + CPU 작업 15개 | 2.022 | 0.587배 | 0/13 |

CPU 작업 1개의 완료 계산 수 중앙값은 690,000회, 15개는 8,388,608회였습니다. 같은 표본의 총 계산량 약 10.7억 회에 비해 CPU가 더한 몫이 작았고, 이 구현에서는 추가 부하·작업 관리 비용을 상쇄하지 못했습니다. IPC·호스트 스케줄링·전력·열의 개별 원인은 분리 측정하지 않았습니다. native CPU 구현이나 다른 스케줄러까지 모두 느리다는 결론은 아닙니다.

동시 모드의 각 표본에서 CPU와 GPU가 모두 완료한 작업을 확인했고 전체 구간을 정렬해 **중복·누락 없이 정확히 한 번** 처리했는지 검사했습니다. 단순히 두 작업이 대기 중이었다는 사실을 증거로 삼지 않았습니다. CPU 작업자의 실제 `perf_counter` 구간과 CUDA event의 커널 실행 시간을 사용해 중첩의 보수적 하한을 계산했습니다. 모든 동시 표본의 하한이 양수였으며 CPU 1개 조건에서도 최소 약 **0.199초**였습니다.

하한 계산은 GPU 호스트 호출 구간과 CPU 구간의 교집합에서, 호스트 구간 중 커널이 아니었을 수 있는 시간을 전부 뺍니다. 컴파일·결과 복사만 CPU와 겹친 경우에는 실제 커널 중첩으로 인정하지 않습니다. 장시간 실습은 최근 4,096개 배치만 보관하며 잘림을 표시합니다. 벤치마크는 전체 구간을 보관해 검사합니다.

[동시 모드 원시 결과](hashcash-hybrid-benchmark.json)에 모든 반복의 시간·장치별 계산 수·중첩 하한·구간 fingerprint·proof·GPU telemetry를 기록했습니다. 첫 반복은 전체 배치 타임라인도 포함합니다. 이 비교는 프로세스 시작·HTTP·SQLite를 제외한 warmed coordinator 비교이며, CPU에 이미 배정한 마지막 구간을 끝까지 기다리는 비용을 포함합니다.

## 앞·뒤·중간·stride 전략

동일한 10자리 nonce 200만 개와 메시지 28바이트, 난이도 5, 작업자 4개를 사용한 **7회 교차 비교**입니다.

| 방문 전략 | 중앙값 MH/s | 정방향 대비 |
|---|---:|---:|
| 연속 정방향 | 3.345 | 기준 |
| 연속 역방향 | 3.468 | 1.037배 |
| 앞·뒤·중앙 상하 분산 | 3.251 | 0.972배 |
| stride 나머지 분할 | 3.369 | 1.007배 |

모든 전략이 정확히 같은 nonce 집합을 한 번씩 방문했습니다. 역방향도 7회 중 5회만 빨랐고 측정 변동에 비해 차이가 작아 일관된 개선으로 채택하지 않았습니다. 별도로 미리 정한 메시지 12개의 실제 해시에서 첫 유효 nonce까지의 방문 수를 비교했지만, 이것은 해답 위치에 따른 운의 비교이며 실제 동시 취소 시간의 측정은 아닙니다.

SHA-256 결과가 균등하다는 모델에서는 한 번의 성공 확률이 `16^-difficulty`입니다. 아직 확인하지 않은 nonce를 중복 없이 계산하는 것이 중요하며, 앞·뒤·중간 중 특정 위치가 보편적으로 유리하다는 근거는 없습니다. 방문 순서를 바꾸어 이번 메시지를 빨리 찾은 것과 초당 더 많은 해시를 계산한 것은 구분해야 합니다. [전체 전략 원시 값·방문 모델](hashcash-strategies.json)을 참고하세요. 방향별 선택 UI는 추가하지 않았고 재현 가능한 비교 도구로 남겼습니다.

## 검증과 재현

GPU 버퍼의 성공→실패→성공 재사용, uint64 상위·하위 word, 33~35바이트 메시지, GPU 실패 구간 재시도, 실제 CPU spawn, 취소·정리, 저장을 검사했습니다. 독립 검토에서 발견한 ‘유효 proof 이후 다른 CPU 작업 실패 시 저장 누락’, 타이밍 기록의 무한 증가, 호스트 호출만으로 중첩을 주장하던 문제를 수정하고 회귀 검사를 추가했습니다.

Edge에서 실제 CPU·CUDA 중첩→취소→새 유효 proof→브라우저 SHA-256 재계산→영구 기록을 검사했습니다. 테스트는 별도 포트·임시 SQLite를 사용하며 기존 개인 기록은 보존합니다.

최종 검증은 **Python 92개(실제 CUDA 7개 포함), Edge E2E 5개, Vitest 41개, TypeScript·ESLint·빌드 통과**입니다.

준비와 발견 시간을 분리하기 위해 새 Python 프로세스로 CPU·GPU·동시 모드를 각각 한 번씩 실행하고, production `accept()`가 처음 검증된 proof를 반환한 시점을 별도로 계측했습니다. 기존 CUDA 디스크 캐시는 유지했고 같은 한국어 메시지·난이도 3·CPU 작업 1개·임시 SQLite를 사용했습니다. CPU의 준비/첫 proof/정리 완료/저장 포함 시간은 약 0.018/0.161/0.165/0.225초, GPU는 1.075/1.077/1.077/1.137초, 동시 모드는 0.344/0.346/0.464/0.524초였습니다. 순차 실행한 단일 표본으로 OS·파일·드라이버 캐시 조건이 달라질 수 있어 성능 순위나 개선율의 근거로 쓰지 않습니다. [단계별 원시 시간·정의](hashcash-functional-timing.json)를 보존했습니다.

실제 브라우저의 기본 메시지·난이도 8 동시 모드에서는 CPU 750,000회와 GPU 3,247,856,944회를 완료해 nonce `3243428010`, 해시 `000000002414c5ac2781b41a79da1a3cda116fd3133f9767d362a169f45c1efa`를 찾아 저장했습니다. 실제 커널과 CPU 계산의 중첩 하한은 약 0.605초였습니다. 준비 계측은 약 2.363초, 연산·정리 경과는 7.430초로, lazy 컴파일과 준비 비용이 포함된 실습 시간입니다. 서버·브라우저·Node crypto 재검증이 일치했습니다. 이 사례도 고정 계산량 처리량의 개선율과 구분합니다.
