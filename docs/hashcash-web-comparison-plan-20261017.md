# 웹 GPU 단독 / C CPU4+GPU 비교 계획

기준선 `281799f79f01990cf52fba77238977a3feb327b4`를 보존하고 이 PC의 실제 Edge 웹 화면에서 두 모드를 비교한다. 사용자 기록을 사용하는 5187 서버는 측정에 사용하지 않는다. 테스트 서버와 임시 기록 저장소를 별도로 생성하며 GPU 실행은 주 담당자 한 명만 수행한다.

이번 후보는 웹의 `gpu`, `native` 두 개로 한정한다. 두 모드 모두 CPU 입력 수 4를 사용하되 GPU 단독은 CPU 작업을 실행하지 않는다. C/CUDA 연산 코드는 변경하지 않고 시각 계측만 추가한다. GPU 단독은 기존처럼 필요한 자릿수를 탐색 중 처음 준비하므로, 이 일회 준비 비용(최초 소스 구성·컴파일)을 별도 누적해 준비 후 시간에서 뺀다. 반복 배치의 기존 compile 호출·Python 관리 비용은 탐색 비용으로 유지한다.

## 유한 입력 집합

| ID | 메시지 | 난이도 | 시작 nonce | 종료 |
| --- | --- | --- | --- | --- |
| easy | `You are the best of best!!!!` | 3 | `0` | 유효 proof |
| ascii | `You are the best of best!!!!` | 8 | `1000000000` | 유효 proof |
| unicode | `한글🙂` | 8 | `1000000000` | 유효 proof |
| fixed | `You are the best of best!!!!` | 64 | `18446744069414584320` | uint64 끝까지 정확히 4294967296개 |

fixed는 production 웹의 uint64 끝 처리를 그대로 이용하며 별도 고정량 API나 계산 코드를 만들지 않는다. 동일 계산량의 처리 시간과 실제 proof 탐색을 구분한다. proof 탐색에서 두 모드의 완료 계산 수·해답 nonce는 달라도 되며, 이를 원시 자료에 남겨 방문 순서 효과와 속도 효과를 구분한다.

## 반복과 시간 구분

- 새 프로세스에서 ASCII를 GPU 먼저 / C 먼저 각각 한 쌍 측정해 프로세스 첫 사용 비용을 별도로 보관한다. CUDA 디스크 캐시는 삭제하지 않으며 이를 완전한 최초 설치 cold start라고 부르지 않는다.
- 주 비교는 각 입력·모드 준비 실행 1회 후 13쌍이다. 실행 순서를 쌍마다 GPU→C / C→GPU로 바꾼다. 준비 실행과 모든 원시 표본을 보관하며 가장 유리한 nonce를 고르지 않는다.
- `startupElapsed`: 작업 생성부터 장치 자체 검증·초기 준비 종료까지.
- `searchPreparationElapsed`: GPU의 탐색 중 최초 자릿수 준비 비용. C 모드는 20자릿수를 미리 준비하므로 0.
- `preparationElapsed`: 위 두 값의 합.
- `proofElapsed`: 작업 생성부터 첫 독립 검증 proof 수신까지. C는 QPC 기반 C 첫 수신 시각을 사용해 100ms 관찰 지연을 제외한다.
- `proofSearchElapsed`: proofElapsed − preparationElapsed. 커널 내부에서 해답이 발견된 원자적 순간이 아니라, 검증된 배치 해답 수신까지의 시간이다.
- 서버 종료 elapsed와 브라우저 클릭→결과 표시·저장 완료 시간을 별도로 남긴다. 브라우저 표시 시간은 350ms 화면 갱신의 영향을 받는다.

각 표본 전후 GPU 상태를 계산 구간 밖에서 수집한다. 사용자 데스크톱 DWM·브라우저의 그래픽 활동은 종료하지 않고 조건을 기록한다. 다른 CUDA 탐색이나 무거운 CPU 검사는 측정과 겹치지 않는다.

## 합격 및 중단 기준

모든 proof는 Node SHA-256으로 독립 검증하고, 원문·시작 nonce·실제 backend·완료량 합계·저장 기록을 확인한다. C 난이도 8 및 fixed는 CPU/GPU 양쪽 완료량과 커널 겹침 하한을 확인한다. fallback·오류·잘못된 해시·겹치는 미완료 작업이 있으면 해당 실행을 실패로 남기고 원인을 해결한 뒤 영향받는 유한 실험을 다시 한다. 표본당 최대 대기 시간은 90초, native 준비를 포함한 최초 실행은 별도 여유를 둔다.

중앙값·최솟값·최댓값·변동·쌍별 승리 수를 보관한다. 제작자와 별도 검토자가 시계 기준·산술·해시·측정 범위를 점검한다. 기존 Python 검사·화면 검사·빌드를 통과한 뒤 결과와 재현 명령을 제출한다.

## 독립 설계 검토에 따른 관찰 부하 대조

첫 실행 도중 독립 검토자가 보조 HTTP 50ms 관찰이 실제 화면보다 요청을 더 만들어 Python 관리 비용에 영향을 줄 수 있다고 지적했다. 이 13쌍 실행은 계획대로 끝내 원시 자료를 보존하되 `observer50` 대조 자료로 구분한다. 정식 비교는 같은 네 입력·준비 실행·13쌍 교대 순서로 한 번 더 수행하고, 실제 화면의 기존 350ms `/status` 응답만 관찰한다. 계산 중 추가 HTTP 조회는 하지 않는다. 첫 프로세스 사용 표본도 추가 조회가 없는 조건에서 별도 서버 프로세스로 다시 확인한다. 이 변경은 측정 대상 엔진 후보나 입력을 바꾸지 않으며, 추가 관찰 부하의 영향을 확인하기 위한 유한한 재측정이다.

50ms 대조 실행의 최초 자릿수 준비 계측은 compile 호출만 포함했다. 정식 비교 전 검토에 따라 타이머 시작을 같은 코드의 최초 `_kernel` 호출 앞으로 옮겨 소스 구성도 준비에 포함한다. 연산 순서나 커널은 바꾸지 않는다. 두 계측 버전의 소스와 실행 자료를 각각 보존한다.

정식 첫 사용 비교의 두 새 서버는 각각 별도의 빈 `CUPY_CACHE_DIR`을 사용한다. 이로써 처음 필요한 커널을 컴파일하는 비용도 관찰하고, 기존 캐시를 사용한 50ms 대조의 첫 프로세스 표본과 구분한다. 사용자 CUDA 캐시는 지우지 않는다. 드라이버·OS 캐시까지 초기화한 완전 cold start는 아니며, 반복 비교는 기본 캐시가 준비된 현재 웹 사용 조건이다.
