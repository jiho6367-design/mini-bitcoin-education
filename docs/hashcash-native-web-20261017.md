# C CPU+GPU 웹 적용 검증 — 2026-10-17

## 범위와 판정 기준

기준선은 `c95c14b0f9decc9e46cfe5b8b3e1e06588a83aef`이며, 이미 검증한 C 엔진 한 종류를 웹에 연결한다. C/CUDA 계산 코드는 수정하지 않는다. 새 성능 후보 탐색이나 웹 속도 향상률 측정은 이번 작업의 범위가 아니다. 이전 CLI 측정의 처리량은 [기존 보고서](hashcash-native-scheduler-20261017.md)에 남아 있다.

합격 조건은 웹 선택 → 실제 C CPU/CUDA 연산 → 진행 상태 → 중지·재시작 → 독립 해시 검증 → 기존 이름별 SQLite 저장의 연결이다. 메시지 원문, uint64 nonce 문자열, 기존 모드와 참가자 기록을 보존한다. 제작과 별개 담당자가 자원 수명·취소·범위·실패 처리를 읽기 전용으로 검토했다.

## 적용 내용

- `mode: "native"`와 **C · CPU + GPU 동시 연산** 옵션을 추가했다. 선택 시 CPU 기본 작업 수는 `min(4, cpuCount)`이며 변경할 수 있다. 자동 모드는 GPU 우선, Python 동시 모드는 CPU 기본 1개를 유지한다.
- 네이티브 실행은 기존 `NativeScheduler.run()`의 단일 C 호출이다. 작업 할당·CPU 작업·CUDA 호출·결과 수집 사이에 Python 배치 콜백을 넣지 않았다. Python 감시 스레드는 0.1초마다 절대 완료 계산 수를 읽고 취소를 전달한다. 웹은 기존 0.35초 갱신을 유지한다.
- 생성·CUDA 준비·실행·해제는 같은 작업 소유 스레드에서 처리한다. 감시 스레드를 종료하고 합류한 뒤에만 reset/close를 수행한다. C 실행 직전 취소가 유실되지 않도록 취소 요청을 반복 전달한다.
- `2^64` 전체 영역은 `(0, 2^64−1)`개와 `(2^64−1, 1)`개로 나눠 uint64 count 오버플로를 피한다. 완료 계산 수는 구간별 누적값을 더해 문자열로 반환한다. 실행 오류로 원래 범위를 다시 시작하지 않는다.
- CUDA 준비 실패 시 C CPU를 사용한다. C DLL 준비 실패 시 작업을 배정하기 전에 Python CPU로 전환한다. 실행 중 CUDA 실패는 기존 C 엔진이 미완료 구간을 CPU로 재시도한다. 화면은 실제 장치와 이유를 표시한다.
- 최대 8192개 배치 추적을 보관한다. 성공한 완료 배치로만 실제 커널 겹침의 하한을 계산하고, GPU 구간당 QPC 2 tick 오차를 뺀다. 추적이 잘리면 처음 기록한 일부 배치 기준임을 표시한다. 계산 수는 추적 보관 한도와 무관하다.
- C/OpenSSL, Python hashlib와 브라우저 Web Crypto를 통해 해답을 검증한다. 기존 HistoryStore 저장·실패 시 재시도 동작을 재사용한다. 유효한 해답은 정리 오류에도 보존한다.

## 실제 검증 결과

환경은 Windows, Intel Core Ultra 7 356H(논리 CPU 16개), NVIDIA GeForce RTX 5070 Laptop GPU, 프로젝트 `.venv`의 Python 3.13이다. GPU 검사는 주 담당자만 순차 실행했으며 성능 측정으로 해석하지 않는다.

| 검사 | 결과 |
| --- | --- |
| Python 전체 검사, 실제 CUDA 포함 | 126개 통과, 건너뜀 없음 |
| 새 네이티브 웹 수명·오류 검사 | 위 검사 중 16개 통과 |
| TypeScript·ESLint·Vitest·배포 빌드 | 모두 통과, Vitest 41개 |
| Edge 웹 검사 | 7개 통과, 실제 C/CUDA 검사 포함 |
| 화면 확인 | 데스크톱 라이트·390px 모바일 다크, 가로 넘침 없음 |
| 독립 코드 검토 | 차단 문제 없음 |

실제 웹 검사는 공백·줄바꿈·한글·이모지 메시지, 시작 nonce `9007199254740993`, 난이도 64로 CPU와 GPU가 모두 계산하고 커널 겹침 하한이 양수임을 확인한 뒤 중지했다. 이후 새 작업에서 난이도 3 해답을 찾아 Node SHA-256과 브라우저 SHA-256으로 검증하고, 별칭별 기록과 새로고침 후 조회를 확인했다. 테스트는 `work/hashcash-e2e/<UUID>`의 임시 SQLite를 사용했다.

자동 검사로 취소 직전 실행 전환, 감시 스레드 실패에 따른 취소·정리, 정리 완료 전 새 작업 차단, 정확한 절대 진행량, uint64 마지막 값과 전체 영역 분할, C/CUDA 준비 실패 전환, 실행 실패 후 재탐색 금지, 잘못된 해답 저장 거부, 정리 오류 후 정상 해답 보존도 검증했다. 실제 하드웨어 오류를 강제로 발생시키지는 않았으며, 실패·전체 영역 분할 검사는 가짜 백엔드와 기존 C 엔진의 독립 검사로 확인했다.

첫 전체 검사에서 기존 Origin 거절 검사에 Windows 10053 연결 오류가 발생했다. 403 응답 전에 읽지 않은 POST 본문을 남기고 소켓을 닫는 경로를 수정했다. 허용되지 않은 Origin은 100000바이트 이하 본문만 버리며 소켓 읽기 대기 제한을 1초로 설정한다. 전체 처리 시간의 제한은 아니며, 본문을 파싱·실행하지 않는다. 기존 Origin 허용 규칙은 유지했다. 50KB 요청 8회를 모두 403으로 거절하고 작업을 생성하지 않는 회귀 검사와, 수정 후 전체 126개 검사가 통과했다.

```powershell
$env:HASHCASH_TEST_GPU = '1'

.\.venv\Scripts\python.exe -m unittest discover -s hashcash_lab/tests -q

$env:HASHCASH_EXPECT_GPU = '1'

```

현재 PC의 로컬 DLL은 기존 실험과 같은 `82fd0e96e9f9c00faf9b9780ad0465e24cfde74930ce5645e8bd973b24e169cf` SHA-256을 사용한다. DLL·빌드 메타데이터·도구 체인은 Git에 포함하지 않는다. 다른 PC/새 clone에서 필요한 빌드 절차는 README의 C 동시 연산 환경을 따른다. GPU 준비가 불가능한 기기에서도 전환 이유를 표시하며 CPU로 실행할 수 있다.

C 모드는 모든 1~20자리 CUDA 함수를 미리 준비한다. 짧은 탐색에서는 준비 비용이 대부분일 수 있고 화면의 평균 속도는 준비 시간을 포함한다. 이번 웹 검사를 새 성능 개선 측정이나 모든 입력에서의 속도 보장으로 해석하지 않는다.
