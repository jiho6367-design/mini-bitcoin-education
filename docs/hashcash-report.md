측정일: **2026-10-03 한국 시간**. 원본은 [k9102/Nonce](https://github.com/k9102/Nonce), commit `1bca090c5b3796c96b7ac12834cc5f00a05a8892`입니다. 수업 PDF를 비교 대상으로 채택하지 않았습니다.

**추가 개선(2026-10-16):** 이 버전보다 빠른 GPU 결과 전송과 실제 CPU·GPU 동시 모드를 검증했습니다. 최신 코드의 성능·방향별 탐색 비교·검사 결과는 [추가 성능 보고서](hashcash-performance-20261016.md)에 정리했습니다. 아래 수치는 10월 3일의 원본 비교 기록입니다.

## 결론

최신 원본의 다중 프로세스 CPU 계산 처리량이 개선되었습니다. 기본 메시지·16개 프로세스·고정 800만 회·5회 중앙값은 **16.095 → 26.368 MH/s, 1.638배**입니다. 개발 PC의 **RTX 5070 Laptop GPU에서 실제 CUDA 실행·경계 테스트·화면의 자동 선택·브라우저 해시 재검증도 통과했습니다.** GPU 처리량은 아래 별도 측정과 원시 결과에 기록했습니다.

## 같은 계산 규칙

`Original/hashcash_gui.py`, `main.py`, `gpu_search.py`의 입력은 `SHA256(UTF8(message) || ASCII(decimal_nonce))`입니다. 구분자·추가 공백·0 채움이 없고 SHA-256은 한 번 적용합니다. 메시지의 공백·줄바꿈·한글을 그대로 보존합니다. 난이도는 선행 16진수 0 개수이며 한 자리는 4비트, 평균 계산량은 `16^difficulty`입니다. 기존 GUI의 Bits 라벨은 실제 비트 개수와 다르게 동작합니다.

기존 GUI는 nonce 0부터 단일 CPU로 탐색하고 UI 스레드를 차단합니다. 최신 `main.py`는 기본 CPU 다중 프로세스이며 `--gpu`를 지정해야 CUDA를 사용합니다. GPU 실패 시 자동 CPU 전환이 없습니다. 최신 CPU와 GPU는 먼저 전달된 병렬 결과를 채택하므로 최소 nonce를 보장하지 않습니다. 이번 구현도 유효한 해답을 보장하며 병렬 실행 시 원본과 다른 nonce를 찾을 수 있습니다.

독립 검증 벡터:

| 메시지 | nonce | SHA-256 |
|---|---:|---|
| `Pyeongtaek University!` | 8656 | `00028e62333a32b5b6bdf41418f42725f8c21d84dc0b7ff60e4480cc11a8677b` |
| `한글🙂` | 980 | `00091f64964396f15d07238d0d352913789e1dea831702392b3ceb73d6ac99ad` |

Python hashlib와 브라우저 Web Crypto 재계산이 일치했습니다.

## 병목과 개선

원본 CPU는 매 nonce마다 메시지와 숫자 바이트를 합쳐 새 해시 객체를 만들고, 해시 앞의 0 개수를 Python 함수로 셉니다. 새 scanner는 고정 메시지의 SHA-256 상태를 미리 계산하고 복사합니다. 첫 바이트에서 대부분의 실패를 제외하고 필요한 후보에만 나머지 바이트·반 바이트 조건을 검사합니다. hex 문자열은 발견 결과와 표본에만 만들고 반복에는 `range`를 사용합니다. 긴 메시지는 이미 압축한 SHA-256 블록을 재사용하는 이점이 더 큽니다.

React 화면은 Python 다중 프로세스의 완료 보고를 받아 약 0.35초마다 표본을 표시합니다. 확인된 계산 수는 완료 보고를 받은 값이며 중지 시 아직 보고하지 않은 작업은 포함하지 않습니다. 화면의 평균 처리 속도는 장치 준비·프로세스 시작을 포함하므로 아래 계산 처리량과 다릅니다. 짧은 탐색은 시작 비용이 지배할 수 있습니다.

독립 생성 CUDA는 메시지·nonce 자리수·난이도별로 컴파일하고 한 스레드가 연속 nonce를 계산합니다. 첫 입력만 10진수 나눗셈으로 만들고 이후 packed ASCII 자리 올림으로 갱신합니다. 배치 사이에서 진행·중지를 처리하며 자리수·uint64 경계를 넘지 않습니다. 난이도 1~4는 262,144회, 5는 4,194,304회, 6 이상은 8,388,608회를 요청합니다. 실제 배치는 자리수·uint64 경계에서 줄어듭니다. 높은 난이도에서 launch·결과 읽기 비용을 분산하며 낮은 난이도에서는 불필요한 계산량을 줄입니다.

## 공정한 고정 계산량 비교

장비는 Intel Core Ultra 7 356H, 16 logical processors, Windows 11, Python 3.13.15입니다. 원본 `worker()`는 수정 없이 import하고, 한 고정 배치가 끝나면 멈추는 queue/event 어댑터를 사용했습니다. 두 방법은 같은 warmed process pool에서 같은 부분집합을 처리하며 실행 순서를 번갈아 측정합니다. GUI·콘솔·디스크 출력·프로세스 시작을 모두 제외했고 발견 후에도 고정 계산량을 끝까지 수행했습니다.

| 입력 | 프로세스 | 고정 계산 수 | 원본 중앙값 | 개선 중앙값 | 향상 |
|---|---:|---:|---:|---:|---:|
| 원본 기본 메시지, UTF-8 28 bytes | 16 | 8,000,000 | 16.095 MH/s | 26.368 MH/s | 1.638배 |
| 같은 기본 메시지 | 4 | 2,000,000 | 5.207 MH/s | 8.917 MH/s | 1.712배 |

모두 난이도 5·시작 nonce 0·5회입니다. 각 프로세스의 첫 발견 nonce/hash와 마지막 nonce/hash가 모든 반복에서 일치했습니다. [원시 측정 결과와 재현 명령](hashcash-benchmark.json)을 보존했습니다. 이 수치를 모든 장비·메시지·난이도의 발견 시간에 그대로 적용할 수는 없습니다.

## 같은 GPU의 고정 계산량 비교

RTX 5070 Laptop GPU, CuPy 14.2.0, CUDA 12.9에서 원본의 `_KERNEL_SOURCE_TEMPLATE`를 메시지 길이 치환 외에는 수정하지 않고 실행했습니다. 메시지 `GPU hashcash comparison test`(UTF-8 28바이트), 난이도 5, 시작 nonce 1,000,000,000, 고정 **8,388,608회**, **7회 교차 순서**입니다. 초기화·자체 검증·캐시된 컴파일 약 0.787초와 warmup을 제외하고 flag 초기화·launch·동기화·결과 읽기·독립 증명 검사·Python 호출을 포함했습니다. 해답이 나와도 같은 범위를 끝까지 계산했습니다.

| 구성 | 800만 회 배치 분할 | 중앙값 처리량 | 빠른 원본 대비 |
|---|---|---:|---:|
| 원본, 128 blocks × 256 threads | 1회 | 2.841 GH/s | 0.912배 |
| 원본, 기본 1024 blocks × 256 threads | 1회 | **3.114 GH/s** | 기준 |
| 새 코드, **실제 난이도 5 서버 배치** | 4,194,304회 × 2 | **3.309 GH/s** | **1.063배** |
| 새 코드, 대량 단일 배치 | 8,388,608회 × 1 | 3.915 GH/s | 1.257배 |
| 새 코드, 변경 전 작은 배치 | 262,144회 × 32 | 1.567 GH/s | 0.503배 |

주요 결론은 **실제 난이도 5 배치 크기의 계산 처리량이 약 6.3% 개선**되었다는 것입니다. 일곱 번 모두 같은 순번의 빠른 원본보다 짧았습니다. 단일 대량 배치의 25.7% 개선은 별도 구성의 결과입니다. 작은 배치를 반복하면 host 호출과 결과 읽기 비용 때문에 오히려 느려지는 것을 측정해 서버 정책을 조정했습니다. 새 실제 배치 두 번의 합계 중앙값은 약 2.535ms, 빠른 원본은 약 2.693ms입니다.

원본의 기본 launch는 약 10억 회이므로 이 비교에서는 고정 800만 회에 맞춰 스레드당 횟수를 줄였습니다. 원본의 두 grid 크기를 모두 기록하고 더 빠른 것을 기준으로 사용했습니다. 각 방법의 전체 계산 수와 모든 반환 증명이 검증되었습니다. [GPU 원시 결과·환경·변동·재현 명령](hashcash-gpu-benchmark.json), [측정 코드](../hashcash_lab/gpu_benchmark.py)를 보존했습니다. 한 장치·메시지·범위의 warmed scanner 비교이며 서버 전체 처리량·첫 탐색 시간·모든 난이도의 향상을 주장하지 않습니다.

## 원본의 경계 문제

- `--fresh`는 checkpoint만 무시하고 CSV는 다시 읽습니다. CSV에는 메시지가 없고 읽을 때 증명을 검증하지 않아 메시지가 바뀌어도 이전 결과가 사용될 수 있습니다. 새 구현은 탐색마다 상태를 새로 만들고 기존 CSV를 읽지 않습니다.
- GPU의 `msg_words[8]`는 32바이트 용량인데 메시지 35바이트까지 허용합니다. `MSG_WORDS=ceil(message_bytes/4)` 순회 때문에 33~35바이트에서 배열 경계를 벗어납니다. 코드로 확인한 결함이며 원본의 해당 경계에서 실행 결과는 측정하지 않았습니다. 새 코드는 64바이트 word layout을 생성하며 33~35바이트·UTF-8 벡터를 실제 GPU에서 hashlib과 대조했습니다.
- 원본 GPU는 uint64 경계를 확인하지 않습니다. 새 구현은 `2^64−1`에서 종료하며, JavaScript 정밀도 손실을 피하기 위해 API nonce를 문자열로 전달합니다.
- 원본 기본 GPU launch는 1,073,741,824회 계산을 마친 뒤 결과를 읽습니다. 새 배치는 최대 8,388,608회입니다. 개발 PC의 warmed 800만 회 배치는 수 밀리초 수준이었으며 화면 E2E에서 실제 GPU 탐색 중지·재시작을 검사했습니다.

## GPU 실행 환경과 실제 검증

개발 PC에는 RTX 5070 Laptop GPU와 Intel Graphics가 있으며 NVIDIA 드라이버는 591.74입니다. 처음에는 격리한 Python 3.12의 CuPy 확장 모듈이 Windows Application Control에 차단되었습니다. CodeIntegrity 3077 로그가 과거 차단을 확인합니다. 이후 같은 모듈이 정상 import되는 것을 재확인했으며 이 작업에서는 보안 정책을 변경하지 않았습니다. 상태 변화의 원인이나 시점은 확인하지 못했습니다.

현재 실행을 막던 원인은 두 가지였습니다. 기존 CuPy 설치에는 CUDA 헤더·NVRTC 등 toolkit 구성요소가 빠져 실제 커널에서 CUDA headers 오류가 발생했습니다. 별도로 웹 실행기는 CuPy 없는 기본 Python 3.13을 선택했습니다. 프로젝트 `.venv`에 추적된 `requirements-gpu.txt`를 설치하고 실행기가 그 환경을 자동 선택하도록 수정했습니다. 우선순위는 `HASHCASH_PYTHON` → 프로젝트 `.venv` → PATH의 `python`입니다.

검증 환경은 Python 3.13.15, CuPy 14.2.0, NumPy 2.4.6, CUDA runtime·NVRTC 12.9 wheel입니다. 간단한 실제 CUDA 커널이 실행되었고 **실제 GPU 테스트 5개가 모두 통과**했습니다. 자리 올림·자리수 전환·32비트 초과·uint64 끝·부분 스레드·33~35바이트 메시지를 hashlib과 대조하고, 양성·음성 난이도 판정과 실제 탐색을 검사했습니다. 초기 자체 검증과 발견 결과 검증을 통과해야만 앱에서 GPU를 사용합니다.

Edge E2E에서 자동 모드가 `GPU · NVIDIA GeForce RTX 5070 Laptop GPU`를 선택하고 `한글🙂`의 유효 nonce/hash를 찾는 것을 확인했습니다. 같은 결과를 Python hashlib과 브라우저 Web Crypto로 각각 재계산했습니다. 어려운 목표 탐색 중지·CPU 재시작, 지연된 이전 응답 차단도 통과했습니다. 이전의 432개 CUDA 소스 생성·호스트 컴파일 검사는 이 실제 실행 검증과 구분합니다.

추가 화면 검증에서 기본 메시지 `You are the best of best!!!!`, 난이도 7, 시작 nonce 0의 자동 모드가 GPU를 사용했습니다. 완료 보고 85,497,472회 뒤 nonce `78810846`, 해시 `00000002879774675135a8fa0238d6ba3f7f01cd8a382ab1871d5f192c58a8ba`를 찾았습니다. 서버·브라우저·Node crypto의 재계산이 일치했습니다. 서버 경과 시간은 약 0.112초였으며 이미 CUDA 컴파일 캐시가 있는 재실행입니다. 이 발견 시간은 고정 계산량의 원본 비교 수치와 구분합니다.

자동 모드의 GPU 대상은 NVIDIA CUDA입니다. Intel·AMD·Apple GPU는 CPU를 사용합니다. 초기화·컴파일·검증·계산 실패 시 마지막 미확인 범위를 CPU로 재시도합니다. [CuPy 공식 설치 문서](https://docs.cupy.dev/en/stable/install.html)의 `[ctk]` 옵션은 선택 GPU 환경의 런타임·NVRTC 구성 요소를 설치합니다. 최초 준비·자체 검증·새 메시지 컴파일 비용은 아래 warmed 처리량에서 제외하며 실제 화면의 경과 시간에는 포함됩니다.

## 서버 재시작 후 남는 사용자 기록

발견한 유효 결과는 `data/hashcash-history.sqlite3`에 자동 저장합니다. 이름·별칭은 탐색 시작 시 고정하며 메시지 원문·목표 난이도·10진수 nonce·전체 SHA-256·연산 장치·확인된 계산 수·경과 시간·UTC 저장 시각을 함께 보관합니다. nonce와 계산 수는 SQLite와 API에서 문자열로 유지합니다. 별칭은 기록 구분용이며 로그인 계정이나 접근 제한은 아닙니다. 같은 서버의 사용자들이 이름별로 조회할 수 있으며 별도 PC의 파일을 자동 동기화하지는 않습니다.

연산과 자식 프로세스 정리가 끝난 뒤 SHA-256을 다시 계산하여 저장하고, SQLite 트랜잭션 커밋을 마친 경우에만 화면에 저장 완료를 표시합니다. 작업 ID를 고유 키로 사용하므로 같은 결과의 저장 재시도는 중복 행을 만들지 않습니다. 서로 다른 탐색·이름·메시지·목표 난이도는 별도 기록입니다. 저장 시간은 연산 경과 시간에 포함하지 않습니다.

저장소가 일시적으로 실패해도 유효한 발견 결과를 유지하고 오류·재시도 버튼을 표시합니다. 저장을 완료할 때까지 새 탐색이 해당 결과를 덮어쓰지 못하도록 화면과 API에서 막습니다. 실패한 저장은 아직 영구 보관되지 않았으므로 서버를 종료하기 전에 저장 재시도를 완료해야 합니다. 중지·실패·미검증 결과는 발견 기록으로 저장하지 않습니다.

새 서버 인스턴스를 같은 폴더로 실행한 HTTP 테스트에서 현재 작업이 없어져도 이전 기록 ID·nonce·메시지·해시가 그대로 조회되는 것을 확인했습니다. 동시 저장의 단일 행 보장, 잘못된 해시 거부, uint64 문자열 보존, 실패한 저장 후 복구도 검사했습니다. 화면에서는 서로 다른 두 이름과 세 탐색의 난이도별 기록을 새로고침 후 조회·브라우저 재검증·조건 불러오기·전체 JSON 다운로드까지 확인했습니다. 목록은 최근 100개이며 내보내기는 필터에 맞는 전체 기록을 포함합니다. 테스트는 임시 폴더를 사용해 실제 사용자 데이터에 결과를 쓰지 않습니다.

실제 실습 서버에서도 이름 `나`로 GPU 난이도 7의 nonce `78810846`을 자동 저장한 뒤 실행기를 종료하고 다시 켰습니다. 새 서버에는 현재 작업이 없지만 같은 기록 ID·nonce·메시지·해시가 남았으며 브라우저 Web Crypto와 Node crypto 재검증이 통과했습니다. 라이트·다크·390px 모바일 기록 화면도 확인했습니다.

저장 폴더는 `HASHCASH_DATA_DIR` 또는 `--data-dir`로 지정할 수 있습니다. 기본 `data/`는 Git에서 제외합니다. 고정 외부 폴더를 선택하거나 종료 후 저장 폴더 전체를 복사하면 프로젝트 폴더를 옮길 때도 기록을 보관할 수 있습니다.

작업은 전용 worktree와 `codex/hashcash-only`에서 진행했습니다. 다른 채팅의 saved checkout이나 메인 브랜치는 변경하지 않았습니다.
