# 최초 CUDA 준비 개선·난이도 9 웹 비교 — 2026-10-17

이 PC의 기본 메시지·난이도 **9**·시작 nonce **0**에서, C CPU4+GPU 첫 준비 중앙값을 **11.8589 → 10.5659초, 10.90%** 줄였다. 준비를 포함한 첫 해답 수신은 **18.3633 → 17.0683초, 7.05%** 짧아졌다. 각각 새 서버와 별도 빈 CuPy 캐시를 사용한 3회 관측이다. 같은 최초 실행 조건의 후보 GPU 단독은 **14.8876초**여서 C보다 먼저 해답을 반환했다. 최초 실행에는 GPU 단독이 빠르다는 결론이며, 준비된 재실행 추천은 아래 13회 비교 결과와 분리한다.

이전 난이도 8의 C 준비 **12.29초는 과거 관측**이다. 이번 개선율의 기준선은 현재 작업 시작 커밋 `63136751f1263c5d4dd80133efe2504bd43ba5ed`를 같은 PC·난이도 9에서 새로 측정한 값이다. 기준선 원본, 실험 복사본, 원시 값, 후보 소스와 실패 자료를 함께 보존한다.

## 시간이 걸리는 곳과 선택한 개선

기존 C 준비는 실제 입력에 특화한 CUDA 함수들을 개별 컴파일했다. 기본 메시지에서는 digest 자체검증 8개 자릿수, 33·34·35바이트 경계 검사 3개, 탐색의 양성·음성 판정 2개, 실제 탐색 1~20자리 20개로 **총 33개 엔트리**다. 자기검증이 실제 탐색 1·20자리 두 개를 미리 준비하므로 C 연결에서 나머지 18개가 추가됐다. C 드라이버 연결은 모든 20자리 핸들을 요구하므로 사용하지 않을 자릿수를 단순히 빼는 방식은 채택하지 않았다.

새 프로세스·빈 CuPy 캐시에서 한 진단 프로파일의 기존 커널 컴파일·조회 합계는 **10.4135초**였다. 반면 CuPy import는 **0.2402초**, 장치 컨텍스트 활성화는 **0.0910초**였다. 이 커널 합계는 `RawKernel.compile()`과 첫 Function 조회를 계측한 값이며 순수 NVRTC 내부 시간만을 뜻하지 않는다. 자기검증·백엔드 생성·C 연결 같은 바깥 구간은 서로 중첩되므로 이들을 모두 더하지 않는다.

사전에 제한한 후보 A·B만 비교했다.

| 후보 | 준비 방식 | 별도 진단 프로파일의 모듈 컴파일 |
| --- | --- | ---: |
| 기준선 | 같은 33개 함수를 각각 준비 | 개별 컴파일·조회 합계 10.4135초 |
| A | 33개를 이름만 달리한 한 모듈로 준비 | 6.6947초 |
| B | 자기검증 13개+탐색 1·20자리 15개, C용 나머지 18개를 두 모듈로 준비 | 3.1144+3.6490=6.7634초 |
| 적용 코드 확인 | B의 두 단계 구조, GPU 단독은 필요한 자릿수만 지연 준비 | 3.0897+3.8112=6.9009초 |

A와 B의 이 작은 차이는 각 진단 1회이고 처리 순서·열 상태도 같지 않아 우열의 정밀 추정으로 삼지 않는다. A는 GPU 단독에도 20개 탐색 함수를 모두 준비시키므로, 기존 GPU의 필요한 자릿수만 준비하는 성질을 유지하는 **B의 두 단계 구조**를 적용했다. 첫 15개 모듈은 기존 자기검증이 그대로 사용하고, 두 번째 18개 모듈은 `prepare_native_kernels()`에서만 준비한다. GPU 단독의 2~19자리 탐색은 실제 도달한 자릿수만 기존 RawKernel 경로로 준비한다. C 준비 후에는 모든 길이가 준비돼 재사용된다.

커널 함수 이름을 고유하게 바꿔 같은 모듈에 담았으며 SHA-256 함수 본문, nonce 입력, 판정 마스크, 커널 배치·스레드 설정과 C ABI는 유지했다. CuPy의 `RawModule.get_function()`은 RawKernel을 반환하므로, C에는 그 `.kernel`의 실제 Function 핸들을 넘긴다. Module·RawKernel·Function 소유자를 함께 보존하고, 이미 GPU 단독에서 준비한 Function이 있으면 기존 핸들과 RawKernel의 대응을 유지한다. 모듈 컴파일과 모든 함수 조회가 성공한 뒤에만 단계 상태를 게시한다.

**실제 웹의 후보 C 첫 실행 3번째 표본**에서는 두 번의 `RawModule.compile()` 합계가 **10.23825초**로, 준비 **10.56585초의 약 96.9%**였다. 소스 생성 합계는 약 3.75ms, 함수 조회 합계는 약 1.73ms였다. 따라서 적용 후에도 주된 병목은 모듈 준비 경로다. 이 값은 모듈 컴파일 호출 전체의 벽시계 시간이며 순수 NVRTC 시간으로 단정하지 않는다. 별도 진단의 약 6.9초를 웹 준비 10.56초와 섞어 더 큰 개선율을 만들지 않는다. 진단과 웹 사이의 차이를 특정 원인 하나로 설명할 연속 CPU·컴파일러·드라이버 계측은 하지 않았다.

## 웹에서 선택할 모드와 준비된 재실행

이 PC의 이번 기본 메시지·난이도 9에서는 **최초 또는 가끔 실행할 때 자동/GPU 단독을 권한다.** 자동은 CUDA를 사용할 수 있으면 GPU 단독과 같은 탐색 경로를 사용한다. C 자원을 이미 준비한 같은 입력의 반복 실행에서는 **C · CPU + GPU 동시 연산, CPU 작업 4개**가 첫 해답에 작은 우세를 보였다. 실제 웹 기본 설정을 비교한 결과이며 모든 메시지·CPU 수·열 상태의 최적값을 증명한 것은 아니다.

각 모드 준비 실행 1회 뒤 13회씩 실행 순서를 회전·반전해 비교했다. 입력은 최초 실행과 같은 메시지·난이도 9·시작 0이다. GPU와 C 모두 같은 서버 자원 캐시를 사용한다. 정식 표본의 GPU 자원 재사용을 강제 확인했고 C는 준비된 커널·스케줄러 재사용도 확인했다.

준비 제외 첫 해답 중앙값은 GPU 8.16154초, C 8.10687초, Python 동시 8.33054초였다. 결과 DOM이 나타난 시각은 GPU 8.3671초/C 8.3752초이며, 위 표의 저장 후 재실행 가능한 시각과 구분한다. 기존 350ms 갱신을 유지했으므로 C의 서버 첫 해답 우세가 화면 표시 개선으로 이어졌다는 근거는 없다.

모든 표본을 보존했다. 장시간 proof 반복 중 온도 상승과 후반 전후 관측 클럭 하락·실행 시간 증가가 함께 나타났다. 센서는 전후 스냅샷이므로 연속 클럭이나 특정 열제한의 인과 효과를 단정하지 않는다. 이 변동에 비해 C의 작은 우세를 보편적인 속도 개선으로 확대하지 않는다.

GPU만 먼저 준비한 상태에서 C를 처음 선택하는 비용도 남는다. 후보의 준비 실행 한 번에서는 GPU 후 첫 C 연결에 5.837초가 추가로 들었다. 이는 준비된 C 재실행 중앙값과 다른 단발 관측이다. 첫 C 연결 전에도 준비가 끝나 있다고 간주해 빠른 반복 수치를 적용하면 안 된다.

현재 기준선의 준비된 난이도 9 교대 13쌍에서는 GPU/C 첫 해답 중앙값이 **7.53336/7.54397초**였지만, C는 가까운 실행 쌍에서 **11/13회** 이겼고 쌍별 차이 중앙값은 **−151.95ms**였다. 독립 중앙값과 쌍별 승리는 다른 통계량이다. GPU 온도 56→87°C 등 시간 변동을 함께 보존했다. 기준선과 후보는 서로 다른 시간 묶음이므로 버전 사이의 탐색 시간 차이를 묶음 컴파일의 인과 효과로 단정하지 않는다.

## 같은 계산량과 CPU 단독

기본 메시지·난이도 9에서 uint64 마지막 **268435456개**(`18446744073441116160`~`18446744073709551615`)를 해답 없이 끝까지 처리했다. 준비를 제외한 웹 작업 완료·정리 시간이며 순수 GPU 커널 시간과 구분한다. CPU 값에는 실제 웹 경로의 프로세스 실행 관리 비용도 남는다.

| 모드 | 정식 횟수 | 준비 제외 완료 중앙값 | 실제 CPU/GPU 커널 겹침 입증 |
| --- | ---: | ---: | ---: |
| GPU 단독 | 13 | 0.070151초 | 단독 |
| C CPU4+GPU | 13 | 0.064294초 | 13/13 |
| Python CPU1+GPU | 13 | 0.122165초 | 0/13 |
| CPU 단독·16작업 | 5 | 21.274876초 | 단독 |

C의 고정량 중앙값은 GPU보다 8.35% 짧았으나, 쌍별 변화 중앙값은 −1.20%(차이 −0.781ms), 승리는 9/13회였다. 짧은 작업의 변동계수는 GPU 21.07%/C 20.78%였다. 이 값으로 긴 작업이 항상 8.35% 빨라진다고 단정하지 않는다. Python 동시 모드는 이 짧은 범위의 정식 13회 모두 실제 중첩 하한이 0이었다. CPU와 GPU가 계산한 수는 모두 양수지만, 해당 완료 시간을 실제 동시 처리량 증거로 쓰지 않는다. 긴 proof9 탐색에서는 C와 Python 동시 표본 모두 실제 중첩을 확인했다.

CPU 단독·16작업의 같은 난이도 9·시작 0 탐색은 사전에 정한 60초 후 실제 웹 중지 버튼으로 종료했다. 실제 서버 종료는 **60.055초**, 완료 보고는 **792,000,000개**였고 proof는 없었다. **60초 안에 미발견인 우측 검열 1회**이며 60초를 발견 시간으로 기록하지 않는다. 이 조건에서는 CPU 단독을 빠른 선택으로 권하지 않는다.

## 검증과 보존 조건

- `SHA256(UTF8(message) || ASCII(decimal_nonce))`, 선행 16진수 0 난이도, Unicode·공백·줄바꿈·NUL·uint64 문자열을 유지한다. 발견 해시는 독립 SHA-256으로 검증하고 Node SHA-256·브라우저 Web Crypto·저장 기록을 대조한다.
- Python **167개 통과, 건너뜀 없음**이며 실제 CUDA·C를 포함한다. 모듈별 원래 함수 본문 일치, 중복 없는 단계 키, 두 단계의 원자적 게시, RawKernel/Function 소유권, 기존 핸들 유지, 컴파일·조회 실패, 취소·재시작, 실제 스레드 간 자원 전달·35바이트 경계를 확인했다.
- TypeScript·ESLint·Vitest **41개**·배포 빌드 및 실제 Edge 화면 검사 **8개**를 통과했다. GPU/CPU 부하 검사는 성능 측정 구간과 겹치지 않았다.
- GPU 실행은 주 담당자 한 명만 수행했다. 다른 담당자는 소스 검토·GPU 없는 구현·독립 자료 검토를 맡았다. 개인 5187 작업과 기록은 측정하지 않았고, 별도 5188/9188·임시 SQLite를 사용했다. 매 측정 전후 개인 작업 ID가 같음을 확인했다. 개인 기록 10건의 전후 논리 해시 일치를 확인했다. 5187을 개선 코드로 다시 시작했고 연결·작업 대기 상태·기록 보존을 확인했다.
- RTX 5070 Laptop GPU·Intel Core Ultra 7 356H, 논리 CPU 16개 환경이다. 그래픽 데스크톱·Edge가 남아 있는 PC 측정이며 OS·드라이버 캐시를 비우거나 전력·드라이버 설정을 바꾸지 않았다. 센서는 실행 전후 관측이며 연속 열·전력 계측이 아니다.

## 실패 자료와 제한

샌드박스 내 첫 프로파일은 NVRTC 임시 파일 접근 거절로 실패해 성능 수치에서 제외했다. 승인된 실행에서 새 캐시로 다시 진행했다. 후보 A의 첫 C 연결은 RawModule의 RawKernel을 실제 Function으로 오인해 거절됐고 `.kernel` 핸들을 보존하도록 수정했다. 첫 임시 웹 호스트는 메인 스레드 stdin 대기·보조 스레드 HTTP 구조에서 POST 후 상태와 저장을 받지 못해 90초에 실패했다. 로그만으로 대기 원인을 확정할 수 없으며 제품과 같은 메인 HTTP 루프로 바꾼 뒤 재실행했다. 실패 파일과 수정 이유를 보존하고, 실패를 느린 GPU 실행으로 집계하지 않는다.

개선 뒤에도 최초 컴파일이 사라지지는 않는다. 정확한 입력·난이도를 키로 하는 기존 서버 자원 캐시와 CuPy 디스크 캐시는 별개이며 새 입력·난이도, 캐시 축출·오류 폐기·서버 재시작의 준비 비용은 조건에 따라 다르다. 이 결과를 모든 메시지나 난이도의 보편적 배수로 일반화하지 않는다. 준비 포함 첫 해답은 배치가 완료돼 유효한 해답을 수신한 시각이며 GPU 스레드 내부의 처음 일치한 명령 시각을 측정한 값은 아니다. 화면은 350ms 간격 갱신으로 별도 지연이 생긴다.

## 재현

진단 프로파일은 기존 경로를 지우지 않고 **새로운** 캐시와 출력 경로를 지정한다. 프로파일 스크립트는 같은 캐시 경로가 이미 있으면 실패하도록 되어 있다.

아래 `work/` 진단·서버 실행기는 이 실험 폴더 기준이다. 새 clone에서는 압축 근거 자료의 `extra_sources` 경로와 `source_blobs_by_sha256` 원문으로 복원할 수 있다. 뒤의 `npm`·웹 비교 명령은 커밋된 실행기를 그대로 사용한다.

```powershell
.\.venv\Scripts\python.exe work/cold-start-20261017/profile_startup.py --source . --out work/cold-start-20261017/profile-repro.json --cache work/cold-start-20261017/profile-repro-cache
```

웹 전체 묶음은 `work/cold-start-20261017/run_web.mjs`에 순서·별도 기록·빈 캐시 검사가 들어 있다. `cold`는 12개 최초 실행, `candidate`는 준비된 세 GPU 모드, `baseline`은 보존한 코드, `cpu`는 CPU 고정량과 사전 60초 proof 관측이다. 기존 실험 캐시를 재사용하면 최초 실행 검사가 거절되므로 별도 새 실험 폴더로 복사하고 소스 경로를 명시하거나, 아래처럼 서버를 직접 띄워 고유 임시 경로로 실행한다. 다른 GPU 작업과 CPU 부하를 겹치지 않는다.

```powershell
# 첫 터미널: 새 서버와 새 캐시·별도 기록
$env:HASHCASH_PORT = '5188'
$env:HASHCASH_API_PORT = '9188'
$env:CUPY_CACHE_DIR = Join-Path (Get-Location) ('work/cold-repro-cache-' + [guid]::NewGuid())
$env:HASHCASH_DATA_DIR = Join-Path (Get-Location) ('work/cold-repro-data-' + [guid]::NewGuid())
npm.cmd run hashcash

# 두 번째 터미널: C 첫 사용. GPU 첫 사용은 별도 새 서버·새 빈 캐시에서 --modes gpu
node scripts/hashcash-web-benchmark.mjs --base-url http://127.0.0.1:5188 --cases proof9 --modes native --mode-workers gpu=4,native=4,hybrid=1,cpu=16 --repeats 1 --no-warmups --out work/cold-repro-native.json

# 준비 실행 뒤 세 모드 반복 비교
node scripts/hashcash-web-benchmark.mjs --base-url http://127.0.0.1:5188 --cases proof9,fixed9 --modes gpu,native,hybrid --mode-workers gpu=4,native=4,hybrid=1,cpu=16 --repeats 13 --expect-reuse --out work/cold-repro-warm.json
```
